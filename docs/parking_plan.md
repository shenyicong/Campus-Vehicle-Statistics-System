# 停车资源规划（应用输出层）

## 系统定位：算法层与应用层分开

| 层 | 内容 | 是否依赖安装位置 |
|---|---|---|
| 算法层 | YOLO11n 四类检测 → IoU 跟踪 → 虚拟线跨线方向判定 | 否，换摄像机不用改代码 |
| 数据层 | 分车型每小时 / 每日进出量（CSV + Excel） | 否 |
| 场地层 | 分区 / 适用车型 / **实有车位数量**，由本地人员录入 | **是**，换场地必须重新设置 |
| 应用层 | 拥堵治理 + 车位供需对比 + 大 / 小车位配比 | 只需业务口径 |

摄像机可以装在**校门口、停车场入口、园区道路**，系统本体不变；
换位置后只需用 `tools/calibrate_line.py` 重新标定 `LINE_Y`
（俯拍画面默认 0.5 常落在天空 / 建筑空白区）。
本仓库以「校园」为业务示例，不限定具体地点；换场地时只需替换场地车位配置。

**要明确区分两条数据线**：

- **供给侧：实际有多少车位** —— 由**本地人员**按现场录入，代表场地真实可用泊位。
  系统不猜、不写死，也不由视频推算。
- **需求侧：需要多少车位** —— 由「通过虚拟线的分车型**通行流量**」推算，
  是派生结论，不是车位级占用检测。

系统把两者做**供需对比**，回答「车位够不够、哪个区紧张、要不要扩建或改作他用」。

## 场地车位配置（本地人员录入）

配置文件：`data/parking_zones.json`（`config.PARKING_ZONES_JSON`，
可用 `CAMPUS_PARKING_ZONES` 指向别的场地文件）。
仓库内附的校园示例：

```json
{
  "site_name": "校园",
  "zones": [
    {"id": "A", "name": "A 区", "classes": ["sedan", "suv"], "slots": 360,
     "note": "小车位：轿车 / SUV"},
    {"id": "B", "name": "B 区", "classes": ["truck", "bus"], "slots": 180,
     "note": "大车位：客车 / 货车"}
  ]
}
```

字段说明：

| 字段 | 含义 | 约束 |
|---|---|---|
| `site_name` | 场地名称，仅用于展示 | 自由文本 |
| `zones[].name` | 分区名称，如 A 区 / B 区 | 自由文本 |
| `zones[].classes` | 该区可停的车型（可多选） | 必须是 `config.CLASSES` 中的类别且非空 |
| `zones[].slots` | **该区实有车位数量** | 非负整数，0 表示尚未配置 |
| `zones[].note` | 备注 | 选填 |

分区数量、名称、车型组合全部可自定义，例如可以拆成
「A 区 轿车 / SUV 360 位」「B 区 客车 / 货车 180 位」「C 区 货车专用 40 位」。

**两种设置方式**（写同一份 JSON）：

1. 网页看板「场地车位设置」表单：改名称、勾选车型、填车位数量，
   点「保存场地配置」即校验并落盘；支持添加 / 删除分区、放弃修改。
   对应接口 `GET/POST /api/parking_zones`。
2. 文本编辑器直接改文件；或先运行
   `python tools/plan_parking.py --init-zones` 生成模板。

保存时会校验：车位数量不能为负或离谱大、每个区必须选至少一个车型。
另外会给出**覆盖关系提示**：同一车型被多个区服务时需求会重复计入；
某车型未被任何区覆盖时不参与供需对比。

## 从通行量推导车位需求（需求侧）

```text
在场数(第 t 小时) = max(0, 在场数(t-1) + 进入数(t) - 驶出数(t))
分区峰值在场数   = max(该区适用车型逐小时在场数之和)
需求泊位数       = ceil(分区峰值 × (1 + 周转余量))
规划用地面积     = 建议泊位数 × 单车位面积 × 通道系数
```

内置分档（仅用于「建议泊位数 / 用地」的需求侧参考口径，
对应「大区域停货车 / 客车，小车位停 SUV / 轿车」）：

| 分区 | 车型 | 单车位面积 | 说明 |
|---|---|---|---|
| `small` 小车位 | 轿车(sedan) + SUV(suv) | 12.5 ㎡（2.5×5.0 m） | 数量多、周转快，划为普通小车位区 |
| `large` 大车位 | 货车(truck) + 客车(bus) | 42.0 ㎡（3.5×12.0 m） | 车长大、转弯半径大，集中划为大区域 |

默认参数：周转余量 20%、通道系数 1.35、每日开始在场数清零
（模拟夜间清场，避免跨日累计误差）。均可用命令行覆盖。

## 供需对比口径

| 指标 | 定义 | 用途 |
|---|---|---|
| 实有车位 | 本地人员录入的 `slots` | 供给上限 |
| 峰值在场数 | 该区适用车型逐小时在场数之和的最大值 | 需求实测峰值 |
| 需求泊位 | `ceil(峰值 × (1+周转余量))` | 含波动余量的需求 |
| 余量 / 缺口 | `实有车位 - 需求泊位`，负数即缺口 | 是否够用、要不要扩建 |
| 峰值饱和度 | `峰值在场数 / 实有车位` | 实际紧张程度 |
| 需求占用率 | `需求泊位 / 实有车位` | 含余量后的占用程度 |
| 状态 | 见下表 | 快速判断 |

| 状态 | 触发条件 |
|---|---|
| 未配置车位 | 实有车位 = 0 |
| 已超负荷 | 峰值在场数 > 实有车位 |
| 周转余量不足 | 峰值可容纳，但需求泊位 > 实有车位 |
| 接近饱和 | 峰值饱和度 ≥ 80% |
| 供给充足 | 其余情况 |

当按当前样本算出的峰值饱和度 < 20% 且实有车位 ≥ 20 时，
报告会提示「车位明显富余，可考虑改作他用」，并注明短样本会低估需求。

## 使用

```bash
# 默认读 data/reports/hourly.csv + data/parking_zones.json
python tools/plan_parking.py

# 指定某次真实视频评估的报表
python tools/plan_parking.py --hourly data/real_eval_cq_full/reports/hourly.csv \
    --out-dir data/real_eval_cq_full/reports

# 调整参数 / 换场地配置 / 生成配置模板
python tools/plan_parking.py --reserve 0.3 --aisle-factor 1.4 --no-reset-daily
python tools/plan_parking.py --zones D:/other_site.json
python tools/plan_parking.py --init-zones
```

产出（都在 `--out-dir` 下）：

| 文件 | 内容 |
|---|---|
| `parking_plan.md` | 可直接放进课程设计报告的供需分析说明 |
| `parking_plan_zones.csv` | **场地分区供需对比表**（供给侧核心输出） |
| `parking_plan.csv` | 大 / 小车位配比汇总（需求侧参考） |
| `parking_plan_timeline.csv` | 逐小时在场数与通行量 |
| `parking_plan.xlsx` | 以上各表 + 配置提示（需 openpyxl） |

网页看板 `web_dashboard.py` 的「场地车位设置」与「车位供需对比」区块调用
同一套 `parking_plan.load_zones() / save_zones() / compute()`，
不重复实现口径；定时刷新只更新数据，不重建编辑中的表单。

## 真实视频示例（重庆内环高速俯拍，12.1 秒 → 1 个小时桶）

场地配置为校园默认值：A 区（轿车 / SUV）360 位、B 区（客车 / 货车）180 位。
由 `data/real_eval_cq_full/reports/hourly.csv` 推导：

| 分区 | 适用车型 | 实有车位 | 峰值在场 | 需求泊位 | 余量 | 峰值饱和度 | 状态 |
|---|---|---|---|---|---|---|---|
| A 区 | 轿车 / SUV | **360** | 32 | 39 | +321 | 8.9% | 供给充足 |
| B 区 | 客车 / 货车 | **180** | 4 | 5 | +175 | 2.2% | 供给充足 |

- 实有车位合计 **540 个**，需求泊位合计 **44 个**，总体余量 **+496 个**，峰值饱和度 6.7%
- 需求侧参考：建议小车位 39 个、大车位 5 个（88.6% / 11.4%），用地约 941.6 ㎡
- 高峰小时通行 **72 辆次**（拥堵治理依据）
- 配置提示：两个区按当前样本都「车位明显富余」

⚠️ 这段视频只有 12.1 秒，全部数据被压进 1 个小时桶，且是高速双向车流，
结果**只用于演示录入 → 推导 → 供需对比的链路**，不能据此认为
540 个车位真的多了。真实规划需要连续多天、覆盖全部出入口的完整报表。

## 两类决策依据

- **拥堵治理**：`peak_hour` 高峰时段 + `parking_plan_timeline.csv`
  逐小时通行量曲线 → 判断出入口通行能力、安排疏导时段、
  评估是否需增设进出通道。
- **停车资源规划**：本地录入的实有车位 + 分车型峰值在场数 →
  每区余量 / 缺口 / 饱和度 → 判断分区是否够用、是否要扩建、
  是否把富余的大车位改作小车位，并给出大 / 小车位配比与用地参考。

## 边界与前提

1. **出入口要统计全**：只统计单个入口时净流入会持续累加，严重高估
   「在场数」。必须同时覆盖出场方向，或多入口合并报表。
2. **方向不能混**：同一画面双向混行时，单条横线把向下记为进、向上记为出；
   停车场若有独立进口 / 出口，建议分车道布两条虚拟线或按 ROI 分流。
3. **样本要连续**：短视频、统计中断、漏检都会低估需求；
   `MIN_TRACK_MOVE` 与检测召回（当前远景小车仍漏约一半）会传导到规划结果。
   因此「车位明显富余」的提示必须结合样本时长判断。
4. **需求下限而非实际占用**：未计入夜间停放、一车多位、临时停靠、
   消防通道、无障碍车位与慢充 / 装卸区。
5. **尺寸为常用参考值**：12.5 / 42 ㎡ 与 1.35 通道系数应按本地
   校园 / 城市停车规划规范调整，不能直接作为施工图依据。
6. **供给侧靠人工维护**：实有车位是录入值，不会自动更新；
   车位改造、临时封闭、子区借位后必须同步修改配置，否则对比结果失真。
7. **覆盖关系要检查**：同一车型被多个区服务会重复计算需求，
   未覆盖车型不参与对比；保存与报告都会给出提示，需由本地人员确认。
